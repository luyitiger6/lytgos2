# 为什么需要 LytgOS2

## 模型能回答之后，难题才刚刚开始

把模型接到 Prompt 和几个 Tool 上，已经越来越容易。难的是让 Agent 真正在企业里做事：读取内部知识、操作企业系统、受预算约束、证明它做了什么，并且让一次应用的经验能复用到下一个应用。

这些工作不该由每个应用各自重建一遍，而应该沉淀在共享的 harness 里。

## Demo 到生产之间的四道门槛

1. **定义一个 Agent 要写代码。** 最懂业务的人反而做不了。
2. **云平台要把数据拿走。** 合规和数据驻留要求让企业无法采用。
3. **执行是黑盒。** 没审计、没白名单、没审批，企业不敢上生产。
4. **跑一个容易，跑一群难。** 没有人把“一群 Agent 的操作系统”这一层交给你。

LytgOS2 用自然语言定义 Agent、私有部署、全链路审计与沙箱，以及一整队 Agent 的生命周期与治理，一次拆掉这四道门槛。

## 瓶颈通常在运行环境，而不是模型

让 Agent 在生产环境可靠工作，限制因素通常不是模型，而是环境：Agent 能不能拿到对的上下文、能不能使用受控的 Tool、能不能被隔离运行、能不能证明它做了什么、跨节点协作时消息能不能不丢不重地送达。

这就是为什么 LytgOS2 不是又一个 Agent，而是让一群 Agent 可靠运行和协同的底座。

## Agent runtime 与 Agent Harness OS

Agent runtime 让单个 Agent 跑起来。Agent Harness OS 运行和管理一群 Agent：生命周期、渠道、共享记忆、多租户与治理，以及分布式形态下的跨节点协作。LytgOS2 是后者。

## 企业真正需要控制的东西

- **上下文**——正确的业务知识、当前数据和任务历史。
- **环境**——一个受控的执行场所，并能连接企业系统。
- **能力**——模型、Tool、MCP server、Skill 和凭证，可以扩展，但不会被无限暴露。
- **治理**——身份、授权、策略、审批、沙箱、审计和成本边界。
- **证据与学习**——交付物、审计证据、Trace、评测和反馈。

当每个团队都各自实现这些能力时，企业得到的是一堆 demo 和脚本：规则会漂移，成本不透明，一个应用的事故也无法教会下一个应用。

## 共同的底座，不同的 Agent 团队

同一套 OS 可以支撑不同的 Agent 团队，因为业务层留在内核之外：

| Agent 团队 | 在 LytgOS2 之上增加什么 |
| --- | --- |
| 研发 | 代码仓库、编码 Agent、CI、评审和测试证据 |
| 客服 | 知识、CRM、工单、审批和人工接管 |
| 运维 | Runbook、可观测、受控操作和事故证据 |
| 竞品情报 | 研究、分析、写作和定时交付 |

LytgOS2 提供它们共享的 Runtime 和治理语义；每个团队负责让应用真正有用的业务工作流和验收标准。

## 方向

先做可用的单机运行时内核，再逐步建设底座分布式和跨节点 Agent 协作，每一步都通过真实使用验证。详见[路线图](/zh/docs/roadmap)。
