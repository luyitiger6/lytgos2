# 项目启动提示词提炼

> 来源：LytgOS2 项目窗口。以下提示词按阶段提炼，可直接复用；`[方括号]` 为需要替换的占位符。
>
> 使用方式：从第 1 阶段顺序推进；每个阶段完成后先验收，再进入下一阶段。

---

## 1. 可复用提示词

### 1.1 理解项目文档

```text
请阅读 [项目目录] 下的 [文档列表]，提炼：
1. 项目是什么、目标用户和核心价值
2. 1.0 交付范围与后续扩展边界
3. 架构分层、核心模块和关键流程
4. 文档之间的口径冲突和未决事项
5. 建议的实施顺序和首批可演示成果

只做理解，不修改文件。
```

### 1.2 重写项目理解

```text
基于上述文档，按「产品定位 → 1.0 范围 → 架构 → 核心机制 → 实施与验收」重写一版项目理解。

要求：
- 以最新技术方案为权威，需求文档作为验收下限
- 标出所有冲突，不要自行替项目做未确认的决策
- 明确当前是设计阶段、骨架阶段还是已实现阶段
```

### 1.3 确认产品命名

```text
产品名确定为 [产品名]，CLI 命令为 [CLI 名]。

请把文档中的旧占位名、命令、工作区路径、数据库名、Maven 模块名统一为：
- 产品名：[产品名]
- CLI：[CLI 名]
- 工作区：[.xxx/]
- 数据库：[.xxx/xxx.db]
- Maven 模块：[prefix-*]
- 版本：[产品名 1.0]

同时修复粘连的旧 token，保持正文内容不变。
```

### 1.4 整理 Markdown 格式

```text
整理 [docs 目录] 下所有 Markdown 文档的格式：
- H1/H2/H3 统一编号，补齐无编号章节
- 代码块加语言标记
- 表格分隔行统一为 | --- | --- |
- 产品名与中文之间补空格，清除旧占位名
- 去除行尾空格，保持 UTF-8 无 BOM，文件末尾保留换行

不要改写正文内容；完成后输出每份文档的校验结果。
```

### 1.5 生成 CLAUDE.md

```text
根据项目文档和当前仓库状态，在根目录生成 CLAUDE.md，使用中文，包含：
1. 项目概述与当前状态
2. 权威文档及优先级
3. 命名规范
4. 目标技术栈
5. 架构与核心模块
6. 不可协商的设计规则
7. 已验证的构建/运行命令
8. 实施顺序和工作约定

不要虚构未实现的能力；明确标注骨架阶段、TODO 和扩展边界。
```

### 1.6 生成 1.0 基线

```text
生成 [docs/ReleaseBaseline.md]，作为 1.0 的唯一口径基线。至少包含：
- 产品身份与命名
- 1.0 必须交付 / 明确不做
- 模块清单与扩展模块
- 核心机制约束
- 数据表、Tool、CLI、REST 端点清单
- 验收指标和 Demo
- 文档冲突裁决表
- 实施顺序

遇到文档冲突时给出明确裁决和理由，不要留下模糊项。
```

### 1.7 生成标准开源 README

```text
参考标准开源项目 README，在根目录生成/重写 README.md，使用中文。包含：
- 顶部居中的 Logo、标题、Slogan、徽章
- 项目简介和与相邻概念的对比
- 核心特性
- 架构图
- 快速开始与使用示例
- 配置、项目结构、兼容性
- 文档索引、路线图、安全说明
- 参与贡献、许可证、致谢

明确标注当前处于骨架阶段、哪些命令尚不可用。
```

### 1.8 校验文档一致性

```text
对比 CLAUDE.md 与 README.md：
1. 列出两份文档中的硬性数字、命名、范围、安全边界
2. 判断是否一致
3. 列出仅详略不同、不构成冲突的部分
4. 补齐真正的覆盖缺口，保持各自定位

输出对比表和修改结果。
```

### 1.9 生成架构图

```text
为 README 生成架构图，使用 SVG（或 PNG），放到 [docs/images/] 并嵌入 README 的架构章节。

要求：
- 展示接入层、引擎层、能力层、基础层
- 展示 CLI / Web / Scheduler 三个触发源
- 标注 1.0 范围与扩展阶段边界
- 深色背景、清晰可读、可点击查看大图

完成后校验 SVG/XML 并渲染预览。
```

### 1.10 生成 Logo 并居中标题

```text
为 [产品名] 生成一个炫酷的 SVG Logo，放到 [docs/images/logo.svg]：
- 深色圆角方形底 + 科技纹理
- 渐变主字母或抽象符号
- 轨道、节点或版本徽章
- 发光、星芒等细节

同时把 README 顶部的 Logo、标题、Slogan、徽章居中显示，并把架构图也居中。
```

### 1.11 Maven 多模块初始化

```text
用 Maven 初始化这个项目：
- 根项目 packaging=pom
- 按 [模块清单] 创建多模块
- JDK 21，Spring Boot 3.x
- 每个模块创建最小可编译代码
- 配置 spring-boot-maven-plugin，boot 模块生成可执行 fat JAR
- 执行 mvn clean package 并确保 BUILD SUCCESS
- 启动 boot JAR，验证 health 端点
```

### 1.12 清理根项目源码

```text
根项目应该是 POM 聚合项目，不需要源码。

删除根目录 src/ 和占位 Main.java，更新 IDE 模块配置，确保源码只存在于各子模块。
修改后重新执行 mvn clean package 验证。
```

### 1.13 设置默认 JDK

```text
把本机 Maven 默认 JDK 改为 21：
- 设置用户级 JAVA_HOME
- 验证 mvn -v 显示 JDK 21
- 说明当前已打开终端/IDE 需要重启
- 不要修改系统级 PATH（除非明确要求）
```

### 1.14 验证 boot 入口

```text
验证 [boot 模块] 是否能运行，并说明它是否有 main 函数。

解释 [boot 模块] 与 [cli 模块] 两个入口的分工：
- 哪个是 Spring Boot 可执行入口
- 哪个是 Picocli CLI 骨架
- 哪个还没打成可执行 jar

实际启动 boot JAR 并检查 health 端点。
```

### 1.15 记录后续改造建议

```text
把「CLI/boot 入口改造」的两个方案记入项目记忆，标记为以后改造用，现在不要实现：
1. 保留双入口，把 CLI 打成可执行 jar
2. 做统一启动器，按 chat/serve/gateway 分派
```

### 1.16 提炼提示词

```text
把我在这个窗口里的提示词提炼成一份可复用的提示词文档，写入 [docs/prompt/01.md]。
```

## 5. 2026-11-22 至 2026-11-23 增量提示词

> 本批覆盖：密钥持久化、带密钥的安全扫描、Git 命令行提交、GitHub Actions 查看、自主交付到拉取请求（Pull Request，PR）和绿色持续集成（Continuous Integration，CI）、分支保护、阿里巴巴 Java 开发规约（P3C）阻断、术语规范、本地 Git 钩子和密钥扫描、软件物料清单（Software Bill of Materials，SBOM）缺陷修复。
>
> 核心原则：自动化可以走到「PR + CI 全绿」，合并前必须由人审核；密钥上传、仓库设置变更、force push 等敏感操作仍需明确授权。

### 5.1 持久化外部密钥

```text
把以下外部服务密钥写入 [操作系统] 的用户级环境变量，避免每次构建或联调重复输入：
- NVD_API_KEY=[国家漏洞数据库密钥]
- DEEPSEEK_API_KEY=[DeepSeek 密钥]
- AMAP_API_KEY=[高德地图密钥]

要求：
- 只写入用户级环境变量，不写入仓库文件、日志或提交历史；
- 写入后验证变量存在，输出只显示变量名和长度，不回显明文；
- 说明已经打开的终端或 IDE 需要重启才能读取新值；
- 如果某个服务还有独立的可选凭据（例如 Sonatype OSS Index），要与国家漏洞数据库（National Vulnerability Database，NVD）密钥区分，不要混为一谈。
```

### 5.2 带密钥的安全扫描与 Git 命令行提交

```text
用已配置的 [NVD_API_KEY] 执行完整安全扫描：
1. ./mvnw -B -ntp -Psecurity verify
2. 确认 Dependency-Check 使用 NVD 数据、CycloneDX 生成 SBOM、全部测试通过；
3. 通过 Git 命令行提交当前变更：
   - 提交信息用中文，保留 feat:、fix:、chore: 等英文类型前缀和 Co-Authored-By 尾注；
   - 不提交密钥、构建产物、本地运行数据和无关文件；
   - 提交后报告提交哈希、文件数量、分支状态和是否已推送。
```

### 5.3 查看 GitHub Actions 结果

```text
说明如何在 Git 仓库查看 CI 结果并给出可直接访问的路径：
1. 工作流定义在 [.github/workflows/ci.yml]；
2. GitHub 仓库的 Actions 页面查看全部运行；
```

### 5.4 自主交付到 PR 和绿色 CI

```text
以后完成一个功能或模块，按以下流程自主执行，不必每次询问：
1. 从最新 main 拉功能分支（feat/、fix/、docs/、chore/）；
2. 执行质量门禁（见 5.6）；
3. 提交，提交信息用中文并保留英文类型前缀和 Co-Authored-By 尾注；
4. push 并创建 PR，PR 描述用中文并附构建与验证结果；
5. 跟踪 CI，失败则定位、修复、重推，直到全部必需检查通过；
6. CI 全绿后停下来，汇报 PR 链接、变更摘要、关键文件、测试/扫描结果和残留风险，等待人工审核；
7. 人工明确说「通过/合并」后，再执行 squash 合并、删除功能分支、同步 main，并跟踪合并后的 CI。

禁止：
- 未经审核自行合并；
- 用跳过测试、关闭规则或放宽架构约束的方式让构建变绿；
- 在未授权时上传或轮换密钥、修改仓库设置、force push、删除仓库或发布 tag/release。
```

### 5.5 分支保护与必需检查

```text
为 main 开启分支保护，要求：
- 必须走 PR；
- 必需检查（context 名称）：`Build and quality gates`、`Alibaba P3C gate`、`SBOM`、`OWASP Dependency-Check`、`Secret scan`、`Dependency review`；
- 分支必须最新、线性历史、禁止 force push 和删除分支；
- 管理员同样受限（enforce admins）；
- 0 个强制批准，允许项目所有者在检查通过后自行合并；
- 未解决评论阻止合并。

配置完成后验证保护规则，并在文档中记录如何在 GitHub 页面或 gh CLI 查看。
```

### 5.6 全量质量门禁与 P3C 阻断

```text
完成功能或模块后，执行全量质量门禁：
1. ./mvnw -B -ntp -Psecurity verify
   - 完整 Maven Reactor 的九个模块；
   - 测试、Spotless + google-java-format、Checkstyle、PMD 7、SpotBugs + FindSecBugs、ArchUnit、JaCoCo；
   - Dependency-Check（使用 NVD 数据）和 CycloneDX SBOM。
2. ./mvnw -B -ntp -Pp3c verify
   - 阿里巴巴 Java 开发规约（P3C）门禁；
   - 通过 ASM 9.7 读取 Java 21 class 文件；
   - 清理基线违规后设置 failOnViolation=true；
   - CI 的 p3c job 违规即失败，并上传 pmd.xml。

补充规则：
- 纯 .gitignore、文档或配置类小改动不跑本地全量门禁；
- 如果分支保护要求必需检查，优先把这类小改动并到下一个功能 PR，避免单独消耗一次 CI；
- 日志、监控、应用程序编程接口（Application Programming Interface，API）规范中不能完全自动化的部分，按检查清单人工核对，并写入 PR 的残留风险/未执行项。
```

### 5.7 术语与提交规范

```text
更新回复、PR 描述和文档时：

- 代码标识符、命令、配置键、Maven profile 名、文件名保持原样；
- 提交信息用中文，保留英文类型前缀和 Co-Authored-By 尾注。
```

### 5.8 本地 Git 钩子与密钥扫描

```text
安装并启用本地提交前检查：
1. 安装 gitleaks（[winget/choco]）；
2. git config core.hooksPath .githooks；
3. 验证 git hook run pre-commit；
4. 钩子执行：
   - ./mvnw -q -DskipTests spotless:check
   - gitleaks protect --staged --redact
5. 说明 gitleaks 未安装时钩子只提示并跳过，CI 的 Secret scan 是兜底；
6. 说明 Claude Code 或新终端可能继承旧 PATH，必要时刷新用户 PATH 或重启终端。
```
